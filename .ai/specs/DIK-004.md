# DIK-004: Doctor verification screens on web

## Summary
A doctor who is not approved is sent to a new `/verification` screen instead of the dashboard. The screen shows one panel per status: upload form (`not_submitted`), under review with the submitted date and a 30-second refresh (`pending`), and the reviewer's reason with a new upload form (`rejected`). To make uploads possible, the same-origin proxy now forwards request bodies as bytes (not text) with the original multipart `Content-Type`, capped at 6 MB; the browser API client sends `FormData` without forcing JSON. A doctor revoked while the dashboard is open is sent to `/verification` the next time any request returns `403 verification_required`. Key trade-off: the profile from `GET /api/me/` is the only thing that decides routing (fail closed: anything but `approved` goes to `/verification`), so the web app must be deployed after the DIK-003 backend.

## Architecture Conformance
Rules: company `rules/web/nextjs.mdc`; no `.ai/rules.md` in this repo.
- **Route layer is delivery-only.** `app/verification/page.tsx` fetches the profile, redirects and composes components; the file rules live in `lib/schemas/verification.ts`, the polling and upload call in `useVerification.ts`.
- **API chain.** Component → `useVerification` (feature hook) → `apiFetch` (shared client) → proxy. No component calls `fetch` itself. Server side the page uses `getServerProfile` (existing).
- **Forms.** React Hook Form + Zod; the schema is the single source for the type and the messages.
- **State ownership.** Server state (SWR) for the status; local state for the form. No global store.
- **Shared code.** `LogoutButton` and `ErrorBanner` now have a second consumer, so they move to `src/components/`; `ProfileLoadError` is extracted for the same reason. Nothing is extracted for a single caller.
- **Error handling.** The shared client normalises errors into `ApiError`; the feature (`useVerification`) maps `413`/`429` to words, as DIK-002 did for login.
- **Security.** Cookies stay `httpOnly`; the proxy allowlist grows by exactly two rows; the body cap is enforced server-side before buffering.
- Boy-scout: none beyond the moves. `useDashboardData.ts` untouched.

## Implementation Steps
1. `src/lib/types.ts`: add `export type VerificationStatus = "not_submitted" | "pending" | "approved" | "rejected"`; add `verification_status: VerificationStatus | null` to `UserProfile`; add `VerificationRecord = { status; submitted_at: string | null; rejection_reason: string }`.
2. `src/lib/proxy-path.ts`: add `{GET, ["me","verification"]}` and `{POST, ["me","verification"]}`.
3. `src/lib/read-body.ts`: `readBodyCapped(request, maxBytes)` returns `Uint8Array` or throws `BodyTooLargeError`. Refuse when `Content-Length` is a number over the cap (before touching the stream); otherwise read the stream chunk by chunk and stop as soon as the total passes the cap. Export `MAX_PROXY_BODY_BYTES = 6 * 1024 * 1024`.
4. `src/lib/django.ts`: `body?: string | Uint8Array`; `payload` handling unchanged otherwise.
5. `src/app/api/[...path]/route.ts`: for non-GET read the body with `readBodyCapped` (a thrown `BodyTooLargeError` becomes `413 {message: "The request is too large."}` before any Django call); pass the bytes and the original `Content-Type` (default JSON) to `djangoRequest`; the 401-refresh retry resends the same bytes.
6. `src/lib/api-client.ts`: when `body instanceof FormData`, send it as is and set no `Content-Type`; on `403` with body `code === "verification_required"`, `window.location.replace("/verification")` and throw `ApiError(403, ...)`.
7. `src/lib/schemas/verification.ts`: `MAX_DOCUMENT_BYTES`, `documentFormSchema` (`document`: a `File`, type PDF/JPEG/PNG by MIME or, when the MIME is empty, by extension; non-empty; at most 5 MB) with the two messages from the ticket, and `DocumentFormValues`.
8. `src/components/verification/hooks/useVerification.ts`: `useVerification()` (SWR on `me/verification/` plus an effect that re-checks every 30 s only while the status is `pending` and the tab is visible); `uploadDocument(file)` builds `FormData` with field `document`, calls `apiFetch`, and returns the record; `uploadErrorMessage(error)` maps `413` and `429` to the fixed texts and any other `ApiError` to its own message.
9. `src/components/verification/UploadForm.tsx`: RHF + `zodResolver(documentFormSchema)`; file input (`accept` PDF, JPG, PNG), hint, error text with `role="alert"` association, submit button (label prop: "Submit for review" / "Submit again", "Uploading…" while pending) guarded by `useSingleFlight`; on success `mutate` the SWR cache with the returned record; on failure show the message and keep the input usable.
10. `src/components/verification/VerificationPanel.tsx`: the three panels, loading state (`role="status"`), error banner with Retry; when SWR data becomes `approved`, `router.replace("/")`.
11. Move `LogoutButton.tsx` (+ test) and `ErrorBanner.tsx` to `src/components/`; update imports in `Dashboard.tsx` and `unsupported/page.tsx`.
12. `src/components/ProfileLoadError.tsx`: extracted block; `app/page.tsx` uses it.
13. `src/lib/route-gate.ts`: `RouteDecision` adds `"verification"`; `decideRoute` returns `"verification"` for a doctor whose `verification_status` is not `"approved"` (missing or unknown counts as not approved).
14. `src/app/page.tsx`: redirect `verification` to `/verification`.
15. `src/app/verification/page.tsx`: server component. Unauthorized → `unauthorizedRedirect`; error → `ProfileLoadError`; any decision other than `verification` → `redirect("/")` (the home page then sends a non-doctor to `/unsupported` and an approved doctor to the dashboard); otherwise render the top bar (title "Verification", `LogoutButton`), the doctor's name and `VerificationPanel`.
16. `src/app/register/page.tsx`: add the sentence from the ticket under the subtitle.
17. `README.md` and `.ai/context.md`: document the flow, the byte-safe proxy and its 6 MB cap, and that the web app must be deployed after the DIK-003 backend.

## Acceptance Criteria
- [ ] A newly registered doctor lands on `/verification` showing the upload panel, never on the dashboard.
- [ ] A doctor with status `pending` sees the under-review panel with the submitted date and no upload form. The panel updates to the dashboard within about 30 seconds of an admin approving, without the doctor reloading.
- [ ] A doctor with status `rejected` sees the reviewer's reason and an upload form. Submitting a valid file moves the panel to under review.
- [ ] An approved doctor who opens `/verification` is redirected to `/`. A doctor who is not approved and opens `/` is redirected to `/verification`.
- [ ] Choosing a `.docx`, a 6 MB PDF, or no file is blocked in the browser with the messages above and sends no request.
- [ ] A valid 1 MB PDF, a JPG and a PNG upload successfully, and the file arrives at Django byte-for-byte identical (checked by comparing hashes in a test).

- [ ] A doctor who is revoked while the dashboard is open is sent to `/verification` on the next refresh, not shown a broken dashboard.
- [ ] A server refusal of the upload is shown in plain words, never Django's raw text: `429` shows "Too many uploads. Please wait a while and try again." and `413` shows "The file is larger than 5 MB." The form stays usable.
- [ ] Double-clicking Submit sends one upload request.
- [ ] The Disabled User and unknown-role behavior from DIK-001 is unchanged by this ticket.
- [ ] Doctors with no JavaScript-visible tokens: cookies remain `httpOnly` and the document is never readable by the page after upload.

## Risks & Gotchas
- **Body size.** `src/proxy.ts` excludes `/api` in its matcher, so Next's `proxyClientMaxBodySize` (10 MB) does not apply to the route handler. The handler must enforce its own 6 MB cap, which `readBodyCapped` does. The cap also protects JSON routes.
- **Retry after 401.** The proxy resends the request after refreshing the token. A `ReadableStream` body cannot be reused; reading it into a `Uint8Array` once makes the retry safe.
- **Do not set `Content-Type` for `FormData`.** The browser adds the boundary; forcing JSON breaks the upload.
- **Fail closed, deploy order.** A doctor profile without `verification_status` (an old backend) is sent to `/verification`, where the status call fails. The DIK-003 backend must be live first (it is merged; deploy it before this).
- **Hydration.** The submitted date uses `formatDateTime`, which depends on the viewer's time zone; render it only in the client component to avoid a server/client mismatch.
- **Polling cost.** The status endpoint is polled only while `pending`, every 30 s, not when the tab is hidden.
- **`Cache`/stale profile.** The home page redirect happens on the server from a fresh `/api/me/`; after approval the panel calls `router.replace("/")`, which re-runs the server check, so a stale client cannot show the dashboard to an unapproved doctor.
- **Existing tests** that build a `UserProfile` fixture will need the new field.
- **UI reference.** Closest existing screens: the register card (`max-w-2xl rounded-2xl border border-line bg-surface p-8 shadow-sm`, `BrandHeader`) and the dashboard top bar (`border-b border-line bg-surface`, `text-lg font-bold`, `LogoutButton`). Form controls match `RegisterForm` (`h-11 rounded-xl`, navy submit button, `text-sm text-danger` errors). Rejected reason uses the `warn-soft` box like `ErrorBanner`; pending uses `teal-soft`.

## Decisions during implementation
- `verification_required` is handled in `apiFetch`, not in `useDashboardData.ts` (one place for every call).
- Polling is an effect on the current status, not an SWR `refreshInterval`: SWR schedules its next refresh only after a request, so a status written into the cache by an upload was never checked again (found in QA, see below).
- RHF gives a file input's `FileList` to the schema and ignores `setValueAs` for files, so `UploadForm` uses a `Controller` that passes the first `File`.
- `readBodyCapped` returns `Uint8Array<ArrayBuffer>` so it is a valid `fetch` body type under TypeScript 5.9.
- `UserProfile.verification_status` is required (`VerificationStatus | null`); test fixtures default it to `null` (patient) or `"approved"` (doctor).
- Extra files beyond the ticket table: `read-body.ts` (+test), `useVerification.ts` (+test), `ProfileLoadError.tsx`, and the moves of `LogoutButton`/`ErrorBanner` to `src/components/`.
- `VerificationPanel.tsx` keeps two small private helper components (`Card`, `StatusCard`) beside the exported one; they have no other user.
