# DIK-006: Admin review of doctor certificates on web

## Summary
An admin who signs in to the web app now lands on `/admin/verifications`: a review queue of doctors with tabs Pending, Approved, Rejected and All, each row showing the doctor's details and a time submitted, with **View document**, **Approve** and **Reject** (**Revoke approval** for an approved doctor, with a required reason of 1 to 500 characters). The document opens in a new browser tab through the authenticated same-origin proxy, which now passes a PDF, JPEG or PNG through (it used to replace every non-JSON reply with an error). One request (`status=all`) feeds all four tabs and their counts, refreshes every 30 seconds, and decisions update the list in place. Doctors and patients are kept out of the admin page by the server and by Django. Key trade-off: tab counts come from one full list instead of four filtered requests, which is simpler and always consistent, and is fine at the expected number of doctors, but would need server-side counts or paging if the list grew to thousands.

## Architecture Conformance
Rules: company `rules/web/nextjs.mdc`; `AGENTS.md` (Next.js 16).
- **Delivery-only route.** `app/admin/verifications/page.tsx` fetches the profile, redirects and composes; list behaviour lives in `components/admin`, tab rules in `tabs.ts`, the reason rule in `schemas/verification.ts`.
- **API chain.** Component -> `useVerifications` -> shared `apiFetch` -> proxy. The document link is a plain same-origin `<a href>` (a navigation, not an API call), so no token is ever placed in a URL.
- **Forms.** The reject reason uses React Hook Form + Zod; the schema owns the 500-character rule and its messages.
- **State ownership.** Server state in SWR; the open dialog and the selected tab are local state. The selected tab is not in the URL (not requested; adds nothing a back button would need).
- **Shared code.** `Dialog` moves to `src/components/` because a second feature now uses it. Nothing else is extracted for one caller. `LogoutButton`, `ErrorBanner`, `ProfileLoadError` and `BrandHeader` are reused as they are.
- **Security.** The proxy passes a body through only for the document route, only when the upstream reply is ok and its type is PDF, JPEG or PNG, and adds `Cache-Control: private, no-store`. Anything else keeps the old "generic error" behaviour, so Django can never make the web origin serve HTML or script.
- Boy-scout: none beyond the `Dialog` move.

## Professional Practice
Checked how other review queues work (vendor documentation, so unverified as a standard): [Didit manual review](https://docs.didit.me/console/manual-review), [Zyphe manual review](https://docs.zyphe.com/docs/guides/manual-review), [Knogin review queue](https://knogin.com/developers/review-queue-system), [eKYC manual review workflow](https://nivratti.github.io/ekyc-encyclopedia/05-onboarding-workflow/manual-review-workflow).
- Reviewers open the document from the queue before deciding, and a rejection records a reason against the item. Adopted as designed (View document first; the reason is required, up to 500 characters).
- Every decision is logged with who and when. Already done by the backend (`reviewed_by`, `reviewed_at`); this screen does not show an audit history (out of scope in the ticket).
- Only authorised roles decide. Adopted: server-side gate plus Django's own `403`.
- Sources differ on finality of a rejection and on bulk actions (bulk is called risky because it invites approving without looking). Adopted: a rejected doctor can resubmit (as DIK-003 designed) and there is no bulk action.

## Acceptance Criteria
- [ ] An Admin logging in lands on `/admin/verifications`, and opening `/` redirects there.
- [ ] A Doctor and a Disabled User opening `/admin/verifications` are redirected away, and the admin API calls they could try return `403`.
- [ ] The Pending tab lists pending doctors oldest first with name, specialization, area, phone, email and time submitted, and shows the empty state when there are none.
- [ ] Clicking View document opens a PDF, a JPG and a PNG in a new tab and they display correctly, from the admin session only. The same URL opened while logged out or as a Doctor does not return the file.
- [ ] Approving moves the doctor out of Pending into Approved, and that doctor's dashboard unlocks (checked end to end with DIK-004).
- [ ] Rejecting requires a reason: an empty reason, whitespace only, or 501 characters cannot be submitted. A valid reason moves the doctor to Rejected and the doctor sees it on their verification screen.
- [ ] Revoking an Approved doctor needs a reason, moves them to Rejected, and the doctor is locked out of the dashboard.
- [ ] A decision on a record another admin already decided shows the conflict message and refreshes.
- [ ] Double-clicking Approve or Reject sends one request.
- [ ] A failed request (server down) shows an error banner with Retry and keeps the list visible.
- [ ] Cookies remain `httpOnly` and the proxy still rejects any path outside its allowlist.

## Risks & Gotchas
- **Open redirect or token in URL:** none; the document link is relative and authorised by the `httpOnly` cookie on a same-origin GET.
- **Serving files from the app origin.** The passthrough is the one place Django's bytes become a web-origin response: it is limited to the document route, to ok replies, and to three image/PDF types; `nosniff` and `Content-Security-Policy: sandbox` come from Django and are forwarded. Headless Chrome was checked in DIK-003 QA to render a PDF with that header.
- **Errors in the new tab.** If the document is missing (`404`) or the session ended, the new tab shows the proxy's JSON message, not a styled page. Acceptable for an admin tool; stated here so it is not a surprise.
- **Streaming and the refresh retry.** On a `401` the proxy refreshes the token and calls Django again; the first reply's body is unread and dropped, only the second is streamed.
- **`decideRoute` merge order.** DIK-007 (patients) adds another case later and must rebase.
- **One list for four tabs.** Fine for the expected number of doctors; revisit if it grows large.
- **Time ago.** `timeAgo` reads the clock at render; data arrives after mount, so there is no hydration mismatch, and the 30 s refresh keeps the label fresh enough.
- **UI reference.** Layout follows `/verification` (top bar `border-b border-line bg-surface`, `BrandHeader` with home link, `max-w-4xl` content) and the dashboard's list rows (`PatientCard`: `rounded-2xl border border-line bg-surface p-3.5`, avatar circle with initial, `text-sm text-muted` subtitle, pill buttons). Status colours: teal-soft for pending, `warn-soft` for rejected, navy for approved; buttons use `h-11 rounded-xl bg-navy`/outline like the forms.

## Decisions during implementation
- The conflict message ("This request was already decided by someone else.") is owned by `VerificationList` (a dismissible notice), not by the row or the reject dialog: the refresh after a conflict removes the row that raised it. Rows and the dialog stand down on a `DecisionConflictError` (the dialog just closes).
- `Dialog` moved to `src/components/` as planned; the four doctor dialogs only changed their import path.
- Empty-state texts for the other tabs: "No approved doctors yet.", "No rejected requests.", "No doctors have registered yet." (the ticket only fixed the Pending text).
- `Submitted <time ago>` is lower-cased after "Submitted" so "Just now" reads as one sentence.
- A hook-level test for "the 30 s refresh fails keeps the last list" was dropped as a duplicate of the list-level test (the hook harness did not surface SWR's error state; the list shows it).

## QA findings
- **Fixed (test first): the conflict message vanished with its row.** After another admin decided first, the 409 handler showed the message inside the row and the refresh removed that row at once, so the message could never be read. Moved to a list-level notice with Dismiss; regression tests cover approve, reject, the All tab (single notice), dismiss, and clearing after the next success.
- **Backend observation (not fixed here):** `GET /api/admin/verifications/?status=all` lists only doctors that have a verification record. A doctor who registered but never opened the verification screen has no record yet and is missing from the All tab. In real use the screen creates it on first open, so the impact is small. Belongs to the backend (DIK-003); recorded, not worked around.
- Live browser QA (headless Chrome, real backend on a throwaway Postgres DB, production build): 59 checks held on the final build, including PDF, JPG and PNG opening in a new tab byte for byte with the safe headers and `Cache-Control: private, no-store`; the same address returning no file when logged out, as a doctor, or with a tampered cookie; doctor and patient redirected away and refused by the API; reason rules (empty, whitespace, 501); approve unlocking the doctor within about 30 s; revoke locking out an open dashboard within about 10 s and clearing the patient's doctor; double click sending one request; the error banner with Retry keeping the list; allowlist probes; `httpOnly` cookies; no horizontal scroll at 360, 768 and 1280 px.

## Code review on the PR fixed
- The proxy now sets `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, the fixed `inline; filename="certificate"` and `Cache-Control: private, no-store` itself on a relayed certificate, instead of copying them from Django; only `Content-Length` is taken from the upstream reply.
- A status the web app does not know is shown as itself (underscores as spaces), never as "Not submitted".
- The tab list follows the WAI-ARIA tabs pattern: Left/Right (wrapping), Home and End move and select, and only the selected tab is in the Tab order.
- Second review pass: the relay forwards `Content-Length` only when the upstream reply is uncompressed (no `Content-Encoding`, or `identity`); fetch decodes a compressed body but leaves the compressed length in the headers.
