# DIK-002: Harden the Django backend for deployment

## Summary
Move every secret and environment-specific value out of `settings.py` into environment variables (required ones have no default and stop the server at start-up when missing), add the missing Postgres driver, replace open CORS with an allowlist (empty by default), cap message bodies at 2,000 characters (model column plus serializer), and rate-limit login (per username) and register (per IP). The Next.js login and register routes learn the new `429`. Key trade-off: login is limited per username, not per IP, so one attacker cannot lock out every web user behind the Next.js server's shared IP, at the cost that a known username can be locked for a few minutes on purpose.

## Architecture Conformance
No `.ai/rules.md` or central rule file for the backend exists in this project, so Django conventions apply:
- Configuration is read once in `settings.py` through small pure helpers in `dikonekti/env.py`; no module reads `os.environ` elsewhere.
- The 2,000 limit lives once as `MESSAGE_BODY_MAX_LENGTH` in `messaging/models.py` and is imported by the serializer and the migration check.
- Throttle classes are their own module (`accounts/throttles.py`), views only list them.
- Login and register stay thin; no business logic moves into views.
- Boy-scout: none. Noted but left alone because they are outside the ticket: `db.sqlite3` and `__pycache__/*.pyc` are already tracked in git (the new `.gitignore` stops new files, it does not untrack these).
- Web: the `429` mapping goes in the existing `lib/auth/django-session.ts` seam, so the routes stay delivery-only (company web rules).

## Implementation Steps
1. `Dikonekt_Backend/dikonekti/dikonekti/requirements.txt`: add `psycopg[binary]>=3.2,<4`.
2. `dikonekti/env.py` (new): `env_bool(name, default=False)` (true for `1,true,yes,on`, case-insensitive), `env_list(name)` (comma split, trimmed, empty items dropped), `env_required(name)` (raises `ImproperlyConfigured` naming the variable when unset or blank), `allowed_hosts(debug, raw)` (hosts from `raw`; if empty and debug, `["localhost", "127.0.0.1"]`; if empty and not debug, raise naming `DJANGO_ALLOWED_HOSTS`).
3. `dikonekti/settings.py`: `SECRET_KEY = env_required("DJANGO_SECRET_KEY")`, `DEBUG = env_bool("DJANGO_DEBUG")`, `ALLOWED_HOSTS = allowed_hosts(DEBUG, os.environ.get("DJANGO_ALLOWED_HOSTS"))`, `DATABASES` from `DJANGO_DB_NAME/USER/PASSWORD` (required) and `DJANGO_DB_HOST` (default `localhost`), `DJANGO_DB_PORT` (default `5432`); remove `CORS_ALLOW_ALL_ORIGINS`; add `CORS_ALLOWED_ORIGINS = env_list("CORS_ALLOWED_ORIGINS")`.
4. `dikonekti/settings.py` throttling: add `DEFAULT_THROTTLE_RATES = {"login_minute": "5/min", "login_hour": "30/hour", "register": "5/hour"}` to `REST_FRAMEWORK`, and `CACHES` using `django.core.cache.backends.filebased.FileBasedCache` at `DJANGO_CACHE_DIR` (default `<system temp>/dikonekti-cache`) so counters are shared by every worker process on one host.
5. `accounts/throttles.py` (new): `LoginMinuteThrottle` (scope `login_minute`) and `LoginHourThrottle` (scope `login_hour`), both `SimpleRateThrottle` subclasses whose `get_cache_key` uses the lower-cased, stripped `username` from `request.data` when `request.data` is a dict and the value is a non-empty string (otherwise no throttling for that request); `RegisterThrottle` (scope `register`) keyed with `get_ident(request)`.
6. `accounts/views.py`: set `throttle_classes = [LoginMinuteThrottle, LoginHourThrottle]` on `LoginView` and `[RegisterThrottle]` on `RegisterView`.
7. `messaging/models.py`: `MESSAGE_BODY_MAX_LENGTH = 2000` and `body = models.CharField(max_length=MESSAGE_BODY_MAX_LENGTH)`.
8. `messaging/serializers.py`: in `CreateMessageSerializer` declare `body = serializers.CharField(max_length=MESSAGE_BODY_MAX_LENGTH, allow_blank=True, error_messages={"max_length": "Message is too long (max 2000 characters)."})` (default trimming applies before the length check; blank still reaches `validate`, which keeps "Message cannot be empty.").
9. `messaging/migrations/0002_message_body_max_length.py` (new): a `RunPython` pre-check that raises `RuntimeError` with the count and the remediation when any `body` exceeds 2,000 characters, followed by `AlterField` to `CharField(max_length=2000)`. Reverse of the pre-check is a no-op.
10. `.gitignore`, `.env.example` and `README.md` (backend): list the variables, how to export them, how to run the server, tests, and `migrate`; state the required-variable behavior and that the throttle cache is per host.
11. `dikonekti-web/src/lib/auth/django-session.ts`: `LoginResult.rejected.status` becomes `400 | 401 | 429`; `loginWithDjango` and `registerDoctor` return a `rejected`/`invalid` result with the message "Too many attempts. Please wait a few minutes and try again." for `429` (never the raw `detail`).
12. `dikonekti-web` login and register routes: pass a `429` through with that message and the same JSON shape (`{message}` and `{message, errors: {}}`).
13. `.ai/context.md` and `dikonekti-web/README.md`: point to the backend README for required variables and the test command.
14. Rotation note for the PR description: change the Postgres password, generate a new `DJANGO_SECRET_KEY` (this signs every user out), and say that the old values remain in git history.

## Professional Practice
Searched OWASP and Django REST framework documentation.
- **Per-account counting.** The OWASP Authentication Cheat Sheet says the failed-login counter should be tied to the account rather than the source IP, so an attacker cannot avoid it by switching addresses. The OWASP testing guide and the "Blocking Brute Force Attacks" page add that per-account lockout alone does not stop password spraying (one password across many usernames) and can be abused to lock out other users. ASVS caps failed attempts at 100 per hour per account.
- **Adopted:** per-username limits (5 per minute, 30 per hour, well under the ASVS cap) that return `429` for a short window instead of locking the account, which limits the denial-of-service risk the sources describe.
- **Deliberately different:** the sources recommend layering IP or behavior based limits against spraying. This ticket limits only register by IP. A login IP limit would be wrong today because every web login arrives from the Next.js server's one IP, and forwarding the real client IP safely is a separate piece of work (see Out of Scope). Password spraying across usernames is therefore not covered yet.
- **DRF caveats.** The DRF throttling guide says throttles use the Django cache, that the default local-memory cache is per process, that `NUM_PROXIES` controls how the client IP is read behind proxies, and that the built-in throttles are not a hard security control (spoofable IPs, non-atomic counters). **Adopted:** a file-based cache shared by all worker processes on one host, and the limitation is documented. Multi-host deployments need a shared cache (Redis), which is out of scope.
Sources: [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP: Blocking Brute Force Attacks](https://owasp.org/www-community/controls/Blocking_Brute_Force_Attacks), [OWASP WSTG: Weak Lock Out Mechanism](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism), [DRF Throttling](https://www.django-rest-framework.org/api-guide/throttling/). Search results are summaries; the pages themselves were not opened.

## Rule Constraints
- No `.ai/rules.md` exists; Django conventions apply: settings read from the environment in one place, one source for a shared limit, one module per concern.
- Company web rules (`rules/web/nextjs.mdc`) for the web change: route handlers stay delivery-only (the status mapping lives in `lib/auth/django-session.ts`), errors normalised in one place, `strict` TypeScript.
- Never log or return secrets: the start-up error names the variable, never its value.
- Do not stage `__pycache__`, `db.sqlite3` or any file outside the table.

## Risks & Gotchas
- **Every developer must now set the required variables** or `manage.py` (including `runserver`, `migrate` and `test`) refuses to start. The Postgres password and secret key are no longer available as defaults.
- **The Django test runner needs permission to create a test database**; the local `postgres` user has it.
- **`SECRET_KEY` rotation signs every user out**, and the committed password and key stay in git history; say so in the PR description.
- **Per-process throttle counters:** the file-based cache fixes multiple workers on one host but not multiple hosts. DRF also documents the throttles as non-atomic and spoofable, so this is abuse protection, not a hard security boundary.
- **A known username can be locked for a few minutes on purpose** (accepted), and password spraying across usernames is not covered until the real client IP is forwarded (Out of Scope).
- **Register by IP behind the Next.js server is an aggregate cap** for all web sign-ups (5 per hour in total); acceptable for doctor sign-ups today, but it will block legitimate registrations if volume grows.
- The Django version installed locally (5.2.x) differs from the 4.2 the project was generated with; `requirements.txt` allows 5.x. Check `AlterField` and the cache backend behave the same on both.
- `__pycache__` and `db.sqlite3` are tracked in git; running the server or tests rewrites `.pyc` files. Stage only the files in the table.
- The throttle cache directory is created on first use; the process needs write access to `DJANGO_CACHE_DIR`.

## QA findings fixed during implementation
Server-side QA (live Postgres-backed server, plus a production-like instance with debug off) held on: message limits, malformed bodies, authentication, host and CORS rules, login throttling per username (case and spaces), refresh not throttled, no secrets or tracebacks in responses or logs. It found three defects, each reproduced twice and fixed test-first:
1. **Spoofed `X-Forwarded-For`** bypassed the register limit (10 fake addresses, all allowed). Fix: `REST_FRAMEWORK['NUM_PROXIES']` from `DJANGO_NUM_PROXIES`, default `0` (ignore the header). New `env_int` helper.
2. **Parallel overshoot:** 15 to 19 of 25 simultaneous logins passed a limit of 5, because DRF throttles read, decide and write non-atomically. Fix: `allow_request` runs under a thread lock plus an exclusive file lock beside the cache files, so the limit holds across threads and worker processes on one host (tests: threaded burst with a slowed cache, and a six-process test on the real file cache).
3. **Unwritable cache folder** made login and register return `500`. Fix: default folder is per user (`dikonekti-cache-<user>`), the lock file is mode 0600, and a Django system check (`accounts.E001`) stops start-up naming `DJANGO_CACHE_DIR`.
Not attempted: more than one host (needs a shared cache), real HTTPS, and a multi-worker server such as gunicorn (the multi-process behavior is covered by a test).
