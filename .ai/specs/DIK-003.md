# DIK-003: Doctor verification by certificate, with an admin review role (backend)

## Summary
Add an `admin` role and a `DoctorVerification` record per doctor (`not_submitted` / `pending` / `approved` / `rejected`). A doctor uploads a PDF, JPEG or PNG certificate (5 MB max, type checked from the first bytes, stored in a private folder under a random name). An admin lists, views, approves and rejects (with a reason) through new `/api/admin/` endpoints. Until a doctor is approved, every doctor endpoint except `/api/me/` and `/api/me/verification/` returns `403` with `code: "verification_required"`, the doctor is hidden from `GET /api/doctors/`, cannot be chosen at sign-up, and receives no alerts. Revoking approval clears the doctor from their patients. A data migration approves every existing doctor. Key trade-off: files live on the local disk behind an authenticated endpoint (no object storage, no antivirus), which is simple and private but ties the feature to one host until a later ticket moves it.

## Architecture Conformance
No written architecture rules exist for Django in this repo (`.ai/rules.md` is absent). I follow the layout the code already uses: permission classes in `permissions.py`, request parsing in serializers, views thin, helpers in plain modules.
- `files.py` holds all file rules (sniffing, size, storage, deletion). Views call it; nothing else touches the disk.
- The status rules (who may move from what to what) live in one place, methods on `DoctorVerification` (`submit`, `approve`, `reject`), each locking the row. Views only call them. This keeps the rule in one layer and testable without HTTP.
- `_privacy_problem` is generalised, not copied (boy-scout, in the file the ticket already touches).
- One top-level view class per concern; `verification_views.py` holds related views (the existing apps already group views per file).
- Not touched on purpose: the nested stale backend copies (DIK-009).

## Implementation Steps
1. `accounts/models.py`: add `Role.ADMIN = 'admin'` (max_length 10 is enough); add `User.is_admin` property and `User.verification_status` property (`None` unless doctor; `not_submitted` when no record). Add `DoctorVerification` (OneToOne `user` with `limit_choices_to` doctor, `status` choices default `not_submitted`, `document` FileField with callable storage and `upload_to` returning `verification/<uuid>.<ext>`, `submitted_at`, `rejection_reason` (500), `reviewed_by` FK SET_NULL, `reviewed_at`). Methods `submit(file, ext)`, `approve(admin)`, `reject(admin, reason)`, each in `transaction.atomic()` with `select_for_update()` and a conditional status check; `reject` from `approved` or `pending`; leaving `approved` clears `User.objects.filter(registered_doctor=user).update(registered_doctor=None)`. Raise a small `InvalidTransition` exception mapped to `409`.
2. `accounts/migrations/0003`, `0004` (generated, then hand-checked; 0004 reverse deletes only records it created is not possible to tell apart, so reverse is a no-op documented in the file).
3. `accounts/files.py`: `sniff(file) -> 'pdf'|'jpeg'|'png'|None` from the first 8 bytes, `validate_document(file)` (non-empty, size `<= 5 MB`, type known) raising a serializer-friendly error, `MAX_FILE_BYTES`, `MAX_BODY_BYTES = 6 MB`, `private_storage()` (FileSystemStorage at `settings.MEDIA_ROOT`, read at call time so tests can override), `delete_after_commit(name)` using `transaction.on_commit`, `content_type_for(file)` re-sniffing at serve time.
4. `accounts/permissions.py`: `IsAdmin`; `IsVerifiedDoctor` raising `PermissionDenied({'detail': 'Your account is awaiting verification.', 'code': 'verification_required'})` for a doctor not approved, plain `403` message for non-doctors.

7. `accounts/throttles.py`: `VerificationUploadThrottle(_Serialized, SimpleRateThrottle)`, scope `verification_upload`, key `user.pk`, only counts `POST` (returns no key otherwise).
8. `accounts/serializers.py`: add `verification_status` to `UserProfileSerializer`; `DoctorListSerializer` unchanged; register: accept doctor only if `verification.status == approved`, else error on `registered_doctor_username`; add `DocumentUploadSerializer`, `VerificationStatusSerializer`, `AdminVerificationSerializer`, `RejectSerializer` (reason trimmed, 1 to 500).

## Professional Practice
Source: [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) (a standard-mode search surfaced its summary; I did not open the full page, so the points below are what that summary stated).
- Do not trust the client `Content-Type`; check the file signature, but not as the only control. Adopted: magic-byte check plus a fixed extension allowlist. Different: no image re-encoding or antivirus (out of scope, stated in the ticket).
- Generate a random server-side file name, never client input. Adopted: UUID name.
- Store outside the web root with administrative access only (the sheet ranks a separate host higher). Adopted: private folder, no URL route, authenticated endpoint. Different: same host, because no object storage exists yet.
- Set a file size limit. Adopted: 5 MB, refused early by `Content-Length`.
- The search found nothing authoritative on `Content-Disposition` as a defence. The fixed `filename="certificate"`, `nosniff` and `Content-Security-Policy: sandbox` headers come from the ticket's own design and general web-security practice; marked unverified against this source.

## Test Plan (TDD)
Red list, written first. Names describe the attack.
- `files.sniff` / `validate_document`: valid tiny PDF, JPEG, PNG; `.exe` bytes named `.pdf`; HTML sent as `image/png`; empty file; exactly 5 MB passes, 5 MB + 1 byte refused; PDF header with no body still passes the sniff (type check only, documented); file name ignored.
- `DoctorVerification` transitions (service level): `submit` from `not_submitted` and `rejected`, refused from `pending`/`approved`; `approve` only from `pending`; `reject` from `pending` and `approved`; repeat of the same decision raises `InvalidTransition` and leaves `reviewed_by`/`reviewed_at` unchanged; revoke clears patients' `registered_doctor` and leaves other doctors' patients alone; `submit` after rejection clears the reason and deletes the old file only after commit; DB failure after file write removes the new file.
- Concurrency (`TransactionTestCase`, threads): two simultaneous uploads by one doctor give one success, one `409`, one file left; two admins approving/rejecting the same pending record give one success, one `409`.
- Doctor API: status values in `/api/me/`; doctor with no record reads `not_submitted` and can upload; admin and disabled show `null`; response never contains a path or URL; another doctor cannot read/replace someone else's record (no id in the path, so scoped by `request.user`); admin endpoints give `401`/`403` for anonymous, doctor, disabled; `413` for declared body over 6 MB with nothing written; `400` for missing file; eleventh upload in an hour gives `429` with `Retry-After`, other doctor unaffected, same IP shared by two doctors not shared (key is the user).
- Admin API: list default pending, oldest first, filters `approved`/`rejected`/`all`, bad `status` value gives `400`; document view returns the three headers whatever the doctor's name or upload name; document of a missing/deleted file gives `404` not `500`; reject with empty, whitespace, 501-character reason gives `400`, 500 accepted; unknown id gives `404`.
- Role boundaries (`test_role_boundaries.py`): table-driven: for each of patients, alerts (GET), acknowledge, appointments (GET), appointment status, messages (GET, POST), each role × each doctor status gets the exact expected status code; admin never receives another user's data; every doctor endpoint returns `verification_required` for not_submitted/pending/rejected and succeeds after approval.
- Routing: alert created for a patient whose doctor is approved is routed; after revocation the patient has no doctor and the alert is saved with `doctor=None`; doctor list contains only approved; register with unapproved doctor fails on `registered_doctor_username`; register with `role: "admin"` is rejected.
- `create_admin`: creates role `admin` with a hashed password; refuses an existing username; refuses a weak password; mismatched confirmation fails.
- Settings/checks: DEBUG off and no `DJANGO_MEDIA_ROOT` stops start-up naming the variable; DEBUG on defaults to `.private-media`; `accounts.E003` for unwritable, other-owner and group/world-writable folders; the rate-limit folder check still passes its existing tests after the refactor.
- Migration `0004`: doctors existing before become `approved`, disabled users get no record, running it twice creates no duplicate; reverse runs.
- Not unit-tested: `admin.py` registration (compiled and loaded by Django check), URL wiring beyond the API tests, README text.

## Acceptance Criteria
- [ ] A new doctor registers with status `not_submitted`, and `/api/me/` shows `verification_status: "not_submitted"`. A Disabled User and an Admin show `null`. A doctor with no verification record reads as `not_submitted` and can upload.
- [ ] A doctor uploads a valid 1 MB PDF, JPEG or PNG and the status becomes `pending`. The response and `GET /api/me/verification/` never contain a file path or URL.
- [ ] A file over 5 MB, a `.exe` renamed to `.pdf`, an HTML file sent with `image/png`, and a request with no file are each rejected with `400` and a clear message, and the status does not change.
- [ ] A request declaring a body over 6 MB is refused with `413` before it is read, and nothing is written to the storage folder.
- [ ] An eleventh upload within an hour by the same doctor returns `429` with `Retry-After`; another doctor is not affected; the limit is not shared through the IP address.
- [ ] A doctor with status `pending` or `approved` who uploads again gets `409`. A doctor with `rejected` can upload again, the status returns to `pending`, the rejection reason is cleared and the old file is deleted.
- [ ] Two simultaneous uploads by the same doctor give exactly one success and one `409`, and exactly one file remains in the storage folder.
- [ ] A Doctor, a Disabled User and an unauthenticated caller each get `403` or `401` on every `/api/admin/` endpoint. An Admin gets `200`.
- [ ] An Admin can list pending records oldest first, open a document, approve one, and reject another with a reason. A reject without a reason, or with a reason over 500 characters, returns `400`.
- [ ] The document response has `Content-Disposition: inline; filename="certificate"`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, whatever the doctor's name or the uploaded file's name was.
- [ ] Approving or rejecting an already approved or rejected record returns `409`, and the first decision's admin and time are unchanged. Two admins deciding the same pending record at once give exactly one success and one `409`.
- [ ] A doctor with status `not_submitted`, `pending` or `rejected` gets `403` with code `verification_required` on patients, alerts, acknowledge, appointments, appointment status and messages, and `200` on `/api/me/` and `/api/me/verification/`.
- [ ] After approval, the same doctor gets `200` on those endpoints.
- [ ] An Admin gets `403` on patients, alerts, acknowledge, appointments, appointment status and messages, and is never served another user's data.
- [ ] `GET /api/doctors/` returns only approved doctors. Registering a Disabled User with an unapproved doctor fails with an error on `registered_doctor_username`.
- [ ] Revoking an approved doctor clears `registered_doctor` for all of that doctor's patients, and their next alert is saved without a doctor.
- [ ] One doctor cannot read, replace or review another doctor's document. A doctor cannot call the admin endpoints.
- [ ] After the migrations, every doctor that existed before is `approved` and every other user has no verification record.
- [ ] `python manage.py create_admin <username>` creates a user with role `admin` after prompting for a password, and refuses a username that already exists.
- [ ] A request to register with `role: "admin"` is rejected.
- [ ] With `DJANGO_DEBUG` off and no `DJANGO_MEDIA_ROOT`, the server does not start and the error names the variable. With debug on and none set, uploads go to `.private-media/`. A storage folder owned by another user or writable by others stops start-up with `accounts.E003`.
- [ ] All existing backend and web tests still pass, and new tests cover each rule above.

## Risks & Gotchas
- `select_for_update` needs a transaction and a real database: the concurrency tests must be `TransactionTestCase` with threads and Postgres (not SQLite).
- `FileField(storage=callable)` is needed so `override_settings(MEDIA_ROOT=...)` takes effect in tests; a module-level storage would freeze the setting at import.
- `PermissionDenied` raised inside `has_permission` bypasses the permission-list order: an unauthenticated user must still get `401`, so `IsAuthenticated` stays first.
- Throttle counts attempts (including invalid files), which is deliberate: it also limits probing.
- A `413` is returned after authentication and throttle, so it consumes one of the ten hourly uploads. Acceptable; noted in the README.
- Deleting the old file must happen in `transaction.on_commit`; in `TestCase` (wrapped in a transaction) on-commit callbacks do not run, so the file-deletion tests use `captureOnCommitCallbacks(execute=True)`.
- Django's default `FILE_UPLOAD_MAX_MEMORY_SIZE` streams larger files to a temp file; the early `Content-Length` check avoids that for honest oversize requests, but a client lying about length is still bounded by the 5 MB check after parsing (the temp file is deleted by Django).
- `appointments/serializers.py` creates appointments for `patient.registered_doctor` like alerts do; it gets the same approved-doctor rule (an appointment for an unapproved doctor is saved with no doctor, matching alerts).
- Data migration `0004` reverse is a no-op (it cannot tell its rows from later ones).
- Deploy order: do not release to users before DIK-004 and DIK-005 (new doctors would be locked with no screen).

## Decisions during implementation
- `FileField` storage is a plain `FileSystemStorage()` instance, not a callable: Django evaluates a callable once at field creation, which froze `MEDIA_ROOT` and broke test overrides. `FileSystemStorage` already follows `MEDIA_ROOT` changes.
- `IsDisabledOrVerifiedDoctor` (new, in `accounts/permissions.py`) is shared by alerts, appointments and messages list endpoints; `alerts/permissions.py` and `appointments/permissions.py` needed no change.
- `User.approved_registered_doctor` is the single way alerts, appointments and messages find a patient's doctor.
- Extra test files beyond the table: `accounts/test_helpers.py`, `test_files.py`, `test_verification_model.py`, `test_create_admin.py`. Two older tests (`messaging/test_message_limit.py`, `accounts/test_throttling.py`) now give their doctor an approved record, because unapproved doctors are refused.
- Django admin shows `DoctorVerification` read-only without the document field: the private storage has no URL, and an edit there would skip clearing a revoked doctor's patients.
- A reject reason sent as a number is converted to text by DRF and accepted. Left as is.
