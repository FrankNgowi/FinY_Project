# DIK-005: Doctor verification screens in the Flutter app

## Summary
A doctor whose certificate is not approved no longer lands on the doctor dashboard (which would only show errors) but on a new `VerificationPage` with one card per status: upload (`not_submitted`), "under review" with the submitted date that re-checks every 30 seconds and moves on by itself (`pending`), or the reviewer's reason with a new upload (`rejected`). The app's `ApiClient` gains a multipart upload that keeps the bearer token and the silent refresh retry, remembers the server's error `code`, and announces a `403 verification_required` (approval withdrawn while the doctor is using the app) so `MyApp` can re-read the profile and swap the doctor back to the verification screen from one place. Disabled Users signing up see the backend's approved-only doctor list and a clearer empty message. Routing fails closed: anything but `approved` (including a missing or unknown status) goes to verification, so the app must be used with the DIK-003 backend. Key trade-off: the project has no Flutter tests and `ApiClient` is a static class calling `http` directly, so a small seam (an injectable HTTP client) is added to make the upload, refresh and routing logic testable.

## Architecture Conformance
There are no written Flutter rules in this repo; I follow what the code does today (services are static classes returning models, screens own their state, models are plain DTOs) and keep new code at least as clean:
- **Models** (`doctor_verification.dart`, `user_account.dart`) are plain data with parsing; no network or UI.
- **Services** hold all HTTP: `VerificationApiService` calls `ApiClient`; the screen never builds a request.
- **Rules in one place**: allowed types, the 5 MB limit and the fixed `413` and `429` messages live in `verification_document.dart` and `verification_api_service.dart`; the screen and tests read them.
- **One place for a withdrawn approval**: `ApiClient` announces it, `MyApp` re-reads the profile, `DashboardPage` routes. No dashboard widget handles it itself.
- **Failure signals**: every load and upload path shows a message (inline card text for the page load, a snackbar for upload errors, as the ticket asks) and is covered by a test.
- **Boy-scout**: `_LogoutButton` moves to a shared widget because it gains its third user. Not touched on purpose: the 3,354-line `dashboard_components.dart` beyond that move, and the existing `ApiClient` refresh-token handling (it saves only the access token; out of scope).

## Implementation Steps
1. `pubspec.yaml`: add `file_picker: ^13.4.0` under `dependencies`; `flutter pub get` updates `pubspec.lock` (with the pinned Flutter 3.41.9; review that nothing unrelated moves).
2. `lib/models/doctor_verification.dart`: `enum VerificationStatus { notSubmitted, pending, approved, rejected, unknown }` with `fromJson`-style `VerificationStatus.parse(String?)` (null or unknown text gives `unknown`); `DoctorVerification` (`status`, `submittedAt` parsed from ISO and kept as a `DateTime`, `rejectionReason`) with `fromJson` and `submittedLabel` ("13 Nov 2026, 10:42", device local time, no new dependency).
3. `lib/models/user_account.dart`: add `final VerificationStatus? verificationStatus` (null for other roles) parsed from `verification_status`; add `bool get needsVerification => isDoctor && verificationStatus != VerificationStatus.approved` (a missing or unknown value counts as not approved).
4. `lib/services/api_client.dart`: (a) `ApiException` gets an optional `code` read from the error body when it is a string; (b) a `@visibleForTesting static http.Client client` replaces the top-level `http.get/post/patch` calls, and `baseUrl` reads `String.fromEnvironment('API_BASE_URL', defaultValue: <current LAN address>)`; (c) `postMultipart(path, field, fileName, bytes, contentType)` builds a fresh `MultipartRequest` per attempt so the token-refresh retry can resend it, with the same bearer header, the same 401 refresh-and-retry-once, and the same error extraction; (d) `static final ValueNotifier<int> verificationRequired`: incremented whenever a response is `403` with `code == 'verification_required'` (the exception is still thrown).
5. `lib/services/verification_document.dart`: `maxDocumentBytes` (5 MB), `validateDocument(String name, int length)` returning the message or null ("Choose a PDF, JPG or PNG file." for a wrong or missing extension, "The file is empty.", "The file is larger than 5 MB."), `contentTypeFor(String name)`, and the fixed message constants.
6. `lib/services/verification_api_service.dart`: `getStatus()` (GET `/me/verification/` to `DoctorVerification`); `upload({fileName, bytes})` (validates first and sends nothing when invalid; POST multipart field `document`; maps `413` to "The file is larger than 5 MB." and `429` to "Too many uploads. Please wait a while and try again." by throwing `ApiException` with those messages; any other `ApiException` keeps the server's own message).
7. `lib/widgets/logout_button.dart`: move `_LogoutButton` as public `LogoutButton` unchanged; `lib/screens/dashboard_components.dart`: delete the class, import the shared one, rename the two call sites.
8. `lib/screens/verification_page.dart`: `VerificationPage({user, onLogout, onApproved, ...})` using the doctor dashboard's look (background `#F3F7F6`, white rounded cards, navy `#1D3557`, warn-soft `#FFF4E5`, teal `#2A9D8F`), app bar "Verification" with `LogoutButton` and `AccessibilityButton`, a header with the doctor's name, and one card per status; `RefreshIndicator` re-checks the status; a 30 s `Timer` runs only while pending and the app is in the foreground; the file picker and the service are injectable (defaults: `FilePicker.pickFile` limited to pdf, jpg, jpeg and png, and `VerificationApiService`); "Choose file" validates with `validateDocument` and shows the message without sending anything; "Submit for review" / "Submit again" is guarded against double taps, shows a progress indicator, shows a snackbar with the server's message on failure and stays usable, and on success switches the card to pending; on `approved` it calls `onApproved`; every state has `Semantics` labels and the voice assistant (when on) reads the status when the screen opens and when it changes.
9. `lib/screens/dashboard_page.dart`: a doctor with `needsVerification` gets `VerificationPage` (new `onProfileChanged` callback passed through as `onApproved`); an approved doctor gets `DoctorDashboard`; a Disabled User is unchanged. Expose the choice as a small pure function so it can be unit-tested.
10. `lib/app/app.dart`: add `_refreshProfile()` (re-read `/me/`, keep the current user if it fails); listen to `ApiClient.verificationRequired` in `initState` and remove the listener in `dispose`; pass `_refreshProfile` to `DashboardPage`.
11. `lib/screens/create_account_page.dart`: doctor success message "Account created. Next, upload your confirmation letter or certificate."; empty doctor list text "No verified doctors are available yet. You can add one later from your profile."
12. Tests (written first, see Test Plan), then `.ai/context.md`.

## Test Plan (TDD)
The project has no `test/` folder today; `flutter_test` is already a dev dependency, `http` ships `MockClient`, and `flutter_secure_storage` provides `setMockInitialValues`. Written first:
- **`VerificationStatus.parse`** -> each of the four backend values; `null`, empty, wrong case (`Approved`), unknown (`suspended`) all give `unknown`.
- **`DoctorVerification.fromJson` / `submittedLabel`** -> parses an ISO time; `null` and malformed times give a null label; "13 Nov 2026, 10:42" for a known local time; missing rejection reason gives an empty string; reason text is kept verbatim (markup stays plain text).
- **`UserAccount`** -> `verification_status` parsed for a doctor and null for a patient; `needsVerification` is false only for an approved doctor and true for not_submitted, pending, rejected, unknown, null; false for a Disabled User whatever the field says; existing fields still parse.
- **`validateDocument` / `contentTypeFor`** -> pdf, jpg, jpeg, png in any case pass; `.docx`, `.exe`, `.gif`, no extension, `cert.pdf.exe`, a trailing dot fail with "Choose a PDF, JPG or PNG file."; exactly 5 MB passes, 5 MB + 1 byte gives "The file is larger than 5 MB."; zero bytes gives "The file is empty."; wrong type is reported before size; content types are `application/pdf`, `image/jpeg`, `image/png`.
- **`ApiClient`** (with `MockClient`) -> the multipart request carries field `document`, the file name and content type, and exactly the bytes sent (checked in the encoded body, including bytes that are not valid UTF-8); the bearer token is attached; after a `401` the token is refreshed and the same multipart request is resent with identical bytes, once; a `403` with `verification_required` increments the notifier and throws an `ApiException` carrying the code; a `403` with another code, a `400`, a `404` and a `500` do not increment it; error messages still come from `detail` or the first field message as before; the existing GET, POST and PATCH JSON behaviour and the refresh-failure path are unchanged; the error body with a non-string `code` does not crash.
- **`VerificationApiService`** -> `getStatus` parses all statuses; `upload` sends nothing and throws the validation message for a bad file; `413` and `429` give the fixed plain messages (never Django's "Request was throttled" text); `400` shows the server's message; `409` shows "already submitted"; a network failure shows a connection message; success returns the new pending record.
- **`VerificationPage`** (widget tests with fake service and picker) -> each status renders its card (submitted date for pending, the reviewer's reason for rejected, upload for not_submitted); no upload button while pending; choosing a `.docx` or a 6 MB PDF shows the message and sends nothing; a valid file uploads once even when Submit is tapped twice, shows progress, and the card becomes "under review"; an upload failure shows a snackbar, re-enables the button and keeps the chosen file; pull to refresh re-reads the status; while pending the status is re-read every 30 s (fake time) and `approved` calls `onApproved`; no re-reading while not pending; leaving the page stops the timer; the voice assistant text is spoken only when enabled.
- **Dashboard routing** -> the pure choice function for approved, pending, rejected, not_submitted, unknown, null doctors and for a Disabled User; a widget test shows `VerificationPage` for a pending doctor and the doctor dashboard for an approved one (with a `MockClient` answering empty lists).
- **`MyApp` session** -> a restored approved doctor sees the dashboard; when `ApiClient.verificationRequired` fires and `/me/` now says `rejected`, the screen swaps to `VerificationPage`; a failing `/me/` keeps the current screen; the listener is removed on dispose; an approved doctor from `/me/` after `onApproved` opens the dashboard.
- **Sign-up copy** -> a small widget test for the empty-list text and the doctor success text if the page can be built without network (the doctor list call goes through the injectable client).
- **Not unit-tested**: pixel layout, colours and spacing (checked in QA), and the native file picker (replaced by the injectable function in tests; exercised in QA through the web build's real file dialog).

## QA
Target: the Flutter web build served on the Linux dev machine, driven by headless Chrome (`playwright-core`), against a throwaway Django backend on port 8765 and a throwaway Postgres DB (same method as DIK-004 and DIK-006), with `--dart-define=API_BASE_URL=http://127.0.0.1:8765/api` and the backend's `CORS_ALLOWED_ORIGINS` set to the web build's origin. Accounts: a doctor registered through the app's own sign-up, an admin created in the Django shell who approves and rejects through the API, a Disabled User. Data: a small real PDF, JPG and PNG, a `.docx`, a 6 MB PDF, a disguised `.exe`. Checks: sign-up lands on the upload card; invalid files are refused on the device with no request; valid files upload through the real file dialog and the stored file's hash equals the source; under-review card and the 30 s move to the dashboard after approval; rejection shows the reason and allows resubmission; revoke while the dashboard is open swaps back to verification; double tap; `429` and `413` messages; Disabled User sign-up with and without approved doctors; logout from the verification screen. The Android emulator is not used (the machine has too little free memory); the APK is built (`flutter build apk --debug`) so the code compiles for Android. Cannot reach: a physical phone or iOS, and the native Android and iOS file dialogs.

## Acceptance Criteria
- [ ] A newly registered doctor lands on the verification screen with the upload card, not the dashboard.
- [ ] A doctor with `pending` sees the under-review card with the submitted date and no upload button, and is taken to the dashboard within about 30 seconds of approval without reopening the app.
- [ ] A doctor with `rejected` sees the reviewer's reason and can upload again; after a successful upload the card shows under review.
- [ ] An approved doctor goes straight to the dashboard and never sees the verification screen.
- [ ] The file picker offers only PDF, JPG and PNG. A file over 5 MB is refused with the message above and nothing is sent.
- [ ] The upload sends the file unchanged as a multipart request, and a failed upload shows the server's message.
- [ ] A doctor revoked while using the app is returned to the verification screen on the next request.
- [ ] A refused upload is shown in plain words: a `429` shows "Too many uploads. Please wait a while and try again." and a `413` shows "The file is larger than 5 MB.", not Django's raw text.
- [ ] Double-tapping Submit sends one request.
- [ ] A Disabled User signing up sees verified doctors only, and sees the empty-list message when there are none, and can still create the account.
- [ ] Disabled User screens behave exactly as before.

## Risks & Gotchas
- **Do not break the existing session logic.** `MyApp._restoreSession`, the refresh retry and the voice assistant are untouched; the new refresh method only replaces `_currentUser`.
- **Retry of a multipart request.** A `MultipartRequest` can only be sent once, so each attempt builds a new request from the same bytes; a test proves the bytes match on the retry.
- **Fail closed, deploy order.** A doctor profile without `verification_status` (an old backend) goes to the verification screen, where the status call fails and shows an error with a retry; the DIK-003 backend is merged, deploy it before the app.
- **`AccessibilitySettings.of(context)` asserts** that the inherited widget exists: widget tests must wrap pages with it.
- **Timers in tests.** The 30 s status timer and the dashboard's 12 s timer must be cancelled on dispose or `flutter test` reports a pending timer; tests unmount pages before ending.
- **The hard-coded LAN address** is kept as the default so existing setups do not change; only the new `--dart-define` makes it overridable.
- **`file_picker` on Android and iOS** returns a content URI or a temporary copy; the app reads the bytes with `readAsBytes()` and never uses the path.
- **UI reference.** Closest existing screen: the doctor dashboard (`_DoctorDashboardState.build`): `Scaffold` background `#F3F7F6`, `SafeArea`, `RefreshIndicator`, `SingleChildScrollView` padding `(20, 20, 20, 24)`, section titles 20 bold `#14213D`, orange info banner (`#FFF4E5`, 14 radius), cards with 16 radius. The new page reuses those values; the file card uses navy for actions and `#2A9D8F` for the pending state.
